## P0

- [x] **Enabling "Encrypt transcripts" silently writes PLAINTEXT when the OS keychain is unavailable** — area: `src/main/transcripts.ts` (190-201 `writeSaved`, 94-101 `encryptEnvelopeV2`) · effort: M · fix: `writeSaved` only encrypts `if (safeStorage.isEncryptionAvailable())`; otherwise it falls through to `data = Buffer.from(content)` and writes cleartext with **no error and no marker**. On Linux/headless or a locked/denied keychain, every meeting the user believes is encrypted lands on disk (and OneDrive-syncs) in the clear. The API-key vault already has an AES file backend (`secrets.ts`) — route the v2 content-key wrap (`kLocal`) through `encryptSecret()` when `safeStorage` is unavailable, OR fail-closed: refuse the save and surface "encryption unavailable" instead of silently downgrading. · _accept:_ With `safeStorage.isEncryptionAvailable()` forced false and `encryptTranscripts` on, saving a meeting either produces an `ATKENC`-marked encrypted file or returns a visible error — never an unmarked cleartext `.md`.
- [x] **System-audio ("them") can capture silently — empty recap, UI still says "listening", no visible failure** — area: `src/renderer/src/lib/vad.ts` (16-21 thresholds), `src/renderer/src/lib/listen.ts` (281-309 `openChannel`, 422-464 system capture) · effort: M · fix: Both the mic and the system-loopback channel feed the **same** worklet with the **same** fixed VAD thresholds (`ON=0.012`, `OFF=0.006`, `EMIT_RMS=0.005`) tuned for mic-level audio. The system loopback gets no AGC and is often quieter (call app at low volume), so it can never cross `ON`/`EMIT_RMS` → the worklet never emits a window → the "them" side of the whole meeting is silently dropped while the UI shows "listening" and the recap looks complete. There is no level meter or health watchdog on the system channel. Add a `GainNode` (or per-source thresholds) on the `them` channel, and a watchdog: if the `them` channel has been open for N s with zero emitted windows while audio is flowing, surface a soft "not hearing the other side — check call volume / Screen Recording" note. · _accept:_ A low-volume call where the other party is audible still produces `Them:` lines, and if the system channel yields no audio for N s the user sees an explicit note instead of an empty-but-"listening" state.

## P1

- [x] **At-rest key file lives in cleartext next to the ciphertext it protects (defeats encryption in file-backend mode)** — area: `src/main/secrets.ts` (56-63 `useFileBackend`, 79-99 `getOrCreateKey`) · effort: M · fix: Crypto is sound (fresh 12-byte IV per call, GCM tag handled, 32-byte key, `0o600`). The weakness is key storage: in **file-backend** mode `secret-key.bin` sits in `<userData>` alongside `key-*.bin`, `settings.json`, `auth-session.bin`, `msal-cache.bin`, `google-session.bin` — so anyone who can read userData (local backup, second OS user, malware, a copied profile) decrypts every API key + OAuth token + PII context-doc. File backend is used in dev (fine) but ALSO in packaged prod when `safeStorage.isEncryptionAvailable()` is false or `ASKTOTO_LOCAL_KEYSTORE` is set — there at-rest encryption provides ~zero protection. Also `mode:0o600` is a no-op on Windows ACLs. Fix: when `safeStorage` IS available, wrap the file key with `safeStorage.encryptString` (key-encryption-key) so the on-disk key isn't usable from a bare file copy; on Windows set a restrictive ACL; document that pure-file-backend prod is dev-grade only. · _accept:_ On a packaged build with keychain available, `secret-key.bin` on disk is itself encrypted (not a raw 32-byte usable key), and copying userData to another account no longer yields decryptable API keys.
- [x] **Saving / opening a meeting transcript emits NO audit record (events declared but never fired)** — area: `src/main/index.ts` (1065-1081 `saveTranscript`/`saveNote`, 1158-1166 `recallOpen`), `src/main/logger.ts` (52-53) · effort: S · fix: `'transcript.saved'` and `'note.saved'` are in the `AuditEvent` union but `auditLog` is never called for them — the most sensitive operation (writing a full call recording to disk, and decrypting one to a temp file via `recallOpen`/`decryptToTemp`) leaves no trail. Add `auditLog('transcript.saved', { mode, lines, durMin, encrypted })` in the save handlers and a `recall.open`/`transcript.exported` event in `recallOpen` (metadata only — never title/content). · _accept:_ Running a meeting and saving it, then opening it from Recall, each appends a metadata-only line to `logs/audit.log`.
- [x] **System-audio capture spuriously fails as "needs Screen Recording permission" right after the grant** — area: `src/main/index.ts` (1298-1300 `setDisplayMediaRequestHandler`) · effort: S · fix: `desktopCapturer.getSources({types:['screen']})` returns empty transiently for a moment after a fresh Screen-Recording grant; here that yields `callback({})` → `getDisplayMedia` throws `AbortError` → the renderer reports "grant Screen Recording" even though it was just granted. `captureScreenshot` (376-379) already retries once on empty sources; the loopback handler does not. Add the same single 250 ms retry before `callback({})`. · _accept:_ Granting Screen Recording then immediately pressing Listen (system/both) captures the other side on the first try, no spurious permission error.
- [x] **CLI providers pass the full transcript + system prompt as process argv (visible to any local process)** — area: `src/main/cli.ts` (106-122 `buildArgs`, 231-239 `spawn`) · effort: M · fix: `claude -p <prompt>` and `codex exec <prompt>` receive the meeting transcript/screen text and the assembled system prompt as command-line arguments, which are world-readable via `ps -ww`/`/proc/<pid>/cmdline` to every local user/process — a confidential-content leak on shared/managed Macs. Pass the prompt and system text over **stdin** (both CLIs support reading the prompt from stdin) instead of argv. · _accept:_ While a CLI ask is streaming, `ps -ww -p <child>` shows no transcript/prompt text in the argument list.
- [x] **Settings-based SSO gate is renderer-bypassable unless auth is force-enforced** — area: `src/main/auth.ts` (74-85 `readSettingsAzure`, 92-106 `readConfig`, 400-423 `authEnforced`/`requireAuth`), `src/main/index.ts` (686-712 `settingsSet`) · effort: M · fix: When SSO config comes only from in-app Settings (the self-serve path, no env/managed-config), `requireAuth()` returns `!s.configured || s.signedIn`. A compromised/devtools renderer can call `settingsSet` to clear `azureClientId/azureTenantId/azureAllowedDomain` → `configured:false` → `requireAuth` returns `true` without any sign-in — the entire privileged surface unlocks. Only `ASKTOTO_REQUIRE_AUTH`/managed `requireAuth:true` (`authEnforced`) closes this. Fix: treat a previously-configured Azure tenant as sticky/enforced (persist a "was configured" flag that `settingsSet` can't clear without an authed session), or refuse `settingsSet` edits to `azure*` while a session exists and config is active. · _accept:_ With Settings-based SSO configured and a user signed out, clearing the azure fields via IPC does not grant access to gated handlers.
- [x] **Async `setInterval` bodies have no try/catch → a thrown calendar fetch becomes an unhandledRejection + bogus crash dump** — area: `src/main/index.ts` (579-631 `startMeetingNotifier`; cf. 540-571 poller which DOES guard) · effort: S · fix: The notifier's async interval awaits `calendarToday(tz)` with no surrounding try/catch; a throw (network stack, Graph 5xx that rejects rather than returns `{ok:false}`) rejects the interval promise → `onFatal('unhandledRejection')` writes a `crash-*.log` and an `app.crash` audit entry for a benign transient. Wrap the body in try/catch like `startMeetingPoller` does. · _accept:_ Forcing `calendarToday` to reject during a notifier tick logs a warning, not an `app.crash` audit line / crash dump.

## P2

- [x] **No data-deletion or retention controls (GDPR erasure gap)** — area: `src/shared/ipc.ts` (no delete channel), `src/main/recall.ts`, `src/main/transcripts.ts` · effort: M · fix: There is list/search/open/read for saved meetings but no IPC to delete one, no bulk "delete all my data", and no retention/auto-purge policy — call recordings accumulate forever in the OneDrive folder. Add a `recall:delete` handler (basename-guarded, `requireAuth`, audit-logged) and an optional managed-config retention window that prunes transcripts older than N days. · _accept:_ A user can delete a saved meeting from the app, it's removed from disk + index.md, and an audit line records the deletion.
- [x] **Crash dumps + main log can capture secrets/transcript snippets and are never pruned** — area: `src/main/index.ts` (319-351 `onFatal`), `src/main/logger.ts` (11-21) · effort: S · fix: `onFatal` writes `err.stack`/`message` to `crash-<ts>.log` and `mainLog.error`; an unhandled provider rejection can carry a bearer token or transcript fragment in its message, and `crash-*.log` files are written one-per-crash with no rotation/cleanup. Run crash detail through `redactSecrets` before writing, and prune `crash-*.log` to the most recent N on startup. · _accept:_ A crash whose error message embeds an `sk-`/Bearer token writes `[redacted key]` to the dump, and stale crash logs are capped.
- [x] **Decrypted transcript temp copies survive a hard crash** — area: `src/main/transcripts.ts` (216-252 `decryptToTemp`) · effort: S · fix: `recallOpen` writes a cleartext copy to the OS temp dir and only unlinks it on `will-quit`, which does not run on SIGKILL / power loss — leaving a plaintext copy of an "encrypted" transcript behind. Sweep stale `asktoto-*.md` temp files on startup (and/or unlink on window-close, not just quit). · _accept:_ After force-killing the app with a decrypted transcript open, the next launch removes the orphaned cleartext temp file.
- [x] **Google sign-in: id_token signature unverified, no tenant/domain restriction, calendar read ungated** — area: `src/main/google-auth.ts` (248-262 id_token decode), `src/main/index.ts` (838-841 `googleCalendarToday`) · effort: M · fix: Unlike the Azure path (tenant + `@domain` enforced), Google sign-in accepts ANY Google account, decodes the `id_token` payload without verifying its signature (display-only, but still), and `googleCalendarToday` has no `requireAuth` gate. For enterprise parity, add an optional `google.allowedDomain` managed-config check on the email claim and gate `googleCalendarToday` behind `requireAuth`. · _accept:_ With a configured Google allowed-domain, a personal `@gmail.com` account is rejected, and calendar reads require the org sign-in when auth is enforced.
- [x] **redactSecrets misses JWTs and raw OAuth access tokens (incl. the app's own)** — area: `src/shared/redact.ts` (42-52 keyPatterns) · effort: S · fix: Coverage is good for provider keys/cards/SSNs but a bare JWT (`eyJ...`) or an Azure/Google access token pasted/spoken into a transcript is only caught when prefixed with `Bearer`. Add a conservative `\beyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\b` JWT pattern (3-segment, high-confidence) to the cloud-send redaction. · _accept:_ A transcript containing a standalone `eyJ…` JWT is redacted before egress; ordinary base64 words are untouched (unit test).
- [x] **Parakeet silent-empty output is treated as success and never falls back to Whisper** — area: `src/renderer/src/lib/listen.ts` (160-200 `pump`, 247-263 `fallBackToWhisper`) · effort: S · fix: When Parakeet is selected and the native addon returns `''` for every window (model loaded but mis-feeding), `''` resets `parakeetFailures` to 0 and `commitLine` drops it as a phantom — so transcription is silently empty and the 3-strike Whisper fallback never trips. Track consecutive empty-but-"successful" returns over an active-audio window and fall back after a threshold. · _accept:_ A Parakeet session that returns empty for every window while audio is flowing switches to Whisper instead of producing a blank transcript.
- [ ] **System-audio path holds a live 1 fps ScreenCaptureKit video stream for the entire call** — area: `src/main/index.ts` (1294-1300 handler), `src/renderer/src/lib/listen.ts` (430-458 keep-video-track) · effort: M · fix: macOS loopback requires a screen video source, so Métis keeps a full-desktop capture stream running (frames discarded, never saved) for the whole meeting — a real recording indicator + battery/privacy surface that an enterprise security review will question. Investigate dropping the video track to the minimum the SCStream needs, or document the behavior explicitly in the privacy copy. · _accept:_ Either the held video stream is minimized/justified in code comments + privacy docs, or frames are confirmed never retained and the rationale is recorded.

## Audit follow-ups (2026-06-30) — pre-commit 3-agent code review

Three parallel reviewers traced the full uncommitted diff (security/main · IPC/wiring · renderer/UX) before commit. Real defects found and **fixed in this pass**:

- [x] **CLI stdin EPIPE escapes the sync try/catch → false crash dialog + bogus `app.crash` audit** — `src/main/cli.ts` (runCliStream + testCli). A CLI that exits before draining stdin (not-logged-in, or a payload past the 64 KB pipe buffer) raises an async `'error'` on `child.stdin`; the sync try/catch can't catch it, so it hit `onFatal`. Fix: `child.stdin.on('error', () => {})` at both spawn sites.
- [x] **`decryptSecret` off-by-one rejected a valid empty-plaintext envelope** — `src/main/secrets.ts`. Floor was `IV_LEN+TAG_LEN+1`; an empty string encrypts to exactly `IV_LEN+TAG_LEN` (28) bytes. Fixed + locked with `secrets.test.ts` (empty round-trip, IV-uniqueness, tag/ciphertext tamper fail-closed).
- [x] **Silent key regeneration → permanent data loss when a keychain-wrapped key file meets a now-unavailable keychain** — `src/main/secrets.ts` `getOrCreateKey`. The no-keychain branch fell through to `randomBytes(32)`, orphaning every existing encrypted secret/session/transcript-key. Fix: refuse to overwrite a non-empty unreadable key file (fail-closed, recoverable once the keychain returns).
- [x] **`googleCalendarToday` was gated on `requireAuth()`** — `src/main/index.ts`. Contradicted its own comment + the 3 sibling Google handlers; once Azure SSO is enforced it created a dead-end "connect Google" loop. Gate removed (Google is independent of the Mantu/Azure gate; the handler already returns `needsConsent` when not connected).
- [x] **Google domain gate trusted the email claim without `email_verified`/`hd`** — `src/main/google-auth.ts`. When `google.allowedDomain` is set we now also require `email_verified` and an exact Workspace `hd` (hosted-domain) match when present; unverifiable claims fail closed.
- [x] **A started meeting was NOT saved on the Quit / Log out exit paths** — `src/renderer/src/App.tsx` + `Settings.tsx`. Quit/Logout now flush an in-flight meeting (single best-effort save) before teardown, via parent-supplied `onQuit`/`onLogout`.
- [x] **`saveMeetingNow` was best-effort-once and polluted the next session's state** — `src/renderer/src/App.tsx`. Rewrote it to retry with backoff, and to NOT write the live session's `savedRef`/`savedPath` (the meeting it saves is the one being left), fixing both the dropped-meeting and the wrong-"Analyzing"-highlight races.
- [x] **The "not hearing the other side" note was sticky** — `src/renderer/src/lib/listen.ts`. If loopback audio arrived after the 20 s watchdog fired, the note never cleared. Now cleared on the first real `them` window (shared `THEM_SILENT_MSG`, once-guard).
- [x] **Drain re-arm timer untracked + epoch-bail cleared the new session's stop guard** — `src/renderer/src/lib/listen.ts`. `waitForDrain`'s re-arm is now stored in `drainTimerRef`, and an old-epoch bail no longer flips `stoppingRef` belonging to the new session.

Deferred (dormant feature / accepted residual — tracked, not shipped this pass):

- [ ] **Meeting notifier sources only the Outlook calendar cache, not Google events** — `src/main/index.ts` `startMeetingNotifier`. A Google-only user with notifications on gets none. Dormant until calendar OAuth client IDs are provisioned; mirror the cache pattern for Google when wiring it live.
- [ ] **Tray "Quit Métis" / OS window-close does not flush an in-flight meeting** — only the Settings Quit/Log out buttons + reset + New-meeting do. Robust fix is a main-process `before-quit` → renderer flush handshake (with a short timeout cap); accepted as a minor residual for now since the in-app buttons are the primary exits.
- [ ] **⌘Q no longer quits when the overlay is focused** — intentional Cluely-redesign removal of the ⌘Q hijack; quit remains available via the tray and the Settings Quit button. Confirmed not-a-bug.
